## 4. Exact read-only recruiter experience

GET requests still reserve database request budgets, so read-only service use can **write quota counters** and consume database compute/storage/transfer. ## 5. Capacity, service-availability and shared-data risks

The existing [capacity policy](PHASE_B1_CAPACITY_POLICY.md) and [security review](PHASE_B1_SECURITY_REVIEW.md) remain applicable. Defaults are 2,000 admitted API requests/day, 250 writes/day, 64 MiB/day evidence storage plus conservative overhead and a 512 MiB `pg_database_size` write guard. These are shared application budgets, not per-recruiter entitlements or monthly provider billing caps. Failure reservations, repeated attempts and public readers can deny service to other visitors. CORS does not protect records from a direct client.

The policy's 256 MiB warning / 384 MiB investigation thresholds and 50% monthly usage review / 75% write pause / before-90% API suspension are **manual operating recommendations**, not installed alerts. Physical database size is not the provider's exact logical/project/history/branch accounting, and the high-water check is not an atomic allocation guarantee. Do not delete shared records to regain quota without separate retention authorization and a verified backup.

Illustrations, not measured recruiter capacity: 100 CU-hours buys at most 400 active hours at fixed 0.25 CU; 730 always-active hours would consume 182.5 CU-hours. At fixed 2 CU the allowance buys 50 active hours. Anonymous reads, repeated wakes and readiness polling can defeat intended idle savings. Render's shared hours are a separate limit.

Traffic has distinct directions: Render sends frontend/API responses to browsers and SQL/payload traffic to Neon; Neon sends result/export data to Render or the backup operator. Both published transfer allowances matter, as does Render's unquantified external-traffic suspension rule. A large saved evidence export or repeated reads can dominate visits. Existing asset caching helps returning visitors but does not eliminate first-load transfer or API reads. No exact safe visitor count or hosting/FPS performance claim is supported by this audit.

Before a scheduled demonstration, manually load the site once and check actual readiness/error recovery in the authorized environment, allow for real sleep/wake and retain captions/local rehearsal materials as fallback. Do not install periodic keep-alive or pay to avoid cold starts. The build's 90-second frontend API timeout cannot guarantee recovery from provider loading pages or a suspended quota.

## 6. Independent protected backup and recovery

**Proposed genuinely no-additional-cost destination:** an already-owned, owner-controlled disk with an access-restricted encrypted backup directory, plus an already-owned offline/removable second copy if available. No new cloud storage account, subscription or paid scheduler. Existing capacity, encryption/tool availability, owner access and a separately protected recovery key must be verified; no such destination was authenticated or inspected here. If the owner lacks suitable existing storage, the backup gate remains open; do not label this proposal an installed backup service.

Provider PITR/snapshots alone share provider/account risks and do not satisfy independent backup. Neon Object Storage, a branch in the same project, public GitHub, Render ephemeral disk and this temporary cloud workspace are not the selected protected independent destination. Per-ticket JSON/Markdown downloads are useful reports, not a complete database backup. Neon's [backup strategies](https://neon.com/docs/postgres/backup-restore/backups) support native tools; its [pg_dump guide](https://neon.com/docs/manage/backup-pg-dump) specifies a direct/unpooled connection and matching modern clients.

Reuse [runbook steps 18–20](PHASE_B1_HOSTED_RUNBOOK.md) and the existing [native backup probe](../postgres/native_backup_probe.py), [B.0 evidence](PHASE_B0_BACKUP.json) and [B.1 fresh recovery evidence](evidence/b1/B1_FRESH_BACKUP.json). Those prove local synthetic fresh-destination recovery and malformed-archive rejection, not an existing hosted backup. The probe is deliberately local/container-specific; do not run it against provider or live destinations.

Future, separately authorized recovery acceptance:

1. Verify quota headroom and trusted direct-endpoint TLS credentials held only by the owner; export before compute/transfer exhaustion. A suspended quota can also prevent `pg_dump`; waiting for renewal is the allowed fallback, never a paid quota reset.

A local existing PostgreSQL instance can avoid provider branch costs, but its availability is unverified. A provider destination consumes Free limits and needs separate resource authorization.
4. Compare every table, complete evidence, IDs, versions, notes/history, budget/counter rows and idempotent ticket retry behavior. Reapply reviewed runtime grants separately; a `--no-owner` application database dump is not a backup of provider credentials or global roles.
5. Record elapsed recovery time; no measured hosted RTO exists. Retain the current daily-during-writes / before-migration manual backup policy: proposed RPO up to 24 hours **only if backups actually complete**, not a guarantee. Recovery practice and adequate independent copies remain a release gate.
